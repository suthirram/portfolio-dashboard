## 1. The UI mode

### 1.1 Storage and API

`users.ui_mode` (string, `omitempty`): `classic`, `glass` or `ui2`. Absent
means "derive from the legacy `ui_revamp`": `glass` when it is true, else
`classic`. `domain.User.EffectiveUiMode()` is the one place that rule lives,
so the server is correct before, during and after the migration step.

`User` (API) gains the required `ui_mode` enum. `ui_revamp` stays in the
schema until cutover and is now **derived**: `ui_mode == glass`. Every
existing Glass check (`useUiRevamp`, the glass shell, `glass.css`) keeps
working with no change.

`PUT /admin/users/{id}/ui-mode` with `UiModeRequest {mode}`; tier
`tierSuperAdmin`; 403 / 404 / 204 like the other switches. The write sets
`ui_mode` **and** `ui_revamp` (`mode == glass`) in one `$set`, so an older
binary rolled back onto the same data still shows Glass correctly.

The legacy `PUT /admin/users/{id}/ui-revamp` stays and also writes both
fields (`enabled ⇒ glass`, else `classic`). Both endpoints share
`setUserFields`, which `setUserFlag` now delegates to.

### 1.2 Migration step `20261118_01`

One `UpdateMany`: `{ui_revamp: true, ui_mode: {$exists: false}}` →
`$set ui_mode: "glass"`. Accounts without Glass keep no `ui_mode` (derived
`classic`). Idempotent; a single batch; never unsets `ui_revamp` (that
happens at cutover).

### 1.3 Frontend switching

`lib/uiMode.ts` maps the mode to `<html data-ui>`: `glass → "v2"` (unchanged,
so `glass.css` is untouched), `ui2 → "ui2"`, `classic →` attribute removed.
`localStorage.pd_ui` remembers the attribute value as before. `useUiMode()`
returns the account's mode; `useUiRevamp()` is unchanged.

The single switch point is `ShellLayout` (`components/shell/AppShell.tsx`):

```text
ui2     → <Ui2Shell><Outlet/></Ui2Shell>
glass   → <AppShell><Outlet/></AppShell>     (today)
classic → <Outlet/>                          (today)
```

### 1.4 Code layout and isolation

* All UI_2.0 code lives in `frontend/src/ui2/<area>/` (`shell`, `overview`,
  `history`, `transactions`, `dividends`, `gold`, `admin`, `profile`, `auth`).
* Styles: `frontend/src/ui2/ui2.css`, every rule under `:root[data-ui="ui2"]`
  (themes add `[data-theme=…]`). Layout, spacing, typography and the three
  palettes match the owner's handoff mockup
  (`docs/visuals/PD-059-ui-2-reference.html`) 1:1; it is the single source
  of truth for how UI_2.0 looks (owner, 2026-11-18). Only production data,
  wiring and the owner's recorded decisions differ from it.
* Data hooks and services are reused, never copied. When reuse needs logic
  that lives inside a classic component (e.g. `TransactionsModal`'s form
  rules), it is first extracted into a shared hook with no behaviour change,
  proven by the component's existing tests.
* A route the UI_2.0 lane has not built yet renders today's page inside
  `Ui2Shell`. Copies of shell chrome in those pages carry `.shell-dup`
  already (PD-054); `ui2.css` hides them the same way.
* Rollback: switch accounts away (instant), or delete `ui2/` plus the
  `ShellLayout` branch (one PR). Every PR carries the `ui-2.0` label.

## 2. Overall worth

### 2.1 Why a separate collection

The Overview chart covers up to the whole history. A snapshot row embeds its
per-stock lines, so it grows with the number of holdings (about 10 KB at 50
holdings); 10 years of full rows is about 35 MB read per request.
Projection does not help — MongoDB still loads each whole document. A
compact daily document is about 120 bytes regardless of holdings.

Options considered: computing on read from snapshot rows (fresh, but the
read grows with holdings); storing totals on the snapshot row (the same big
read, plus five service write paths and cross-database writes for gold);
**a separate rebuildable collection written by `SnapshotStore`** (chosen).

### 2.2 `portfolio_overall`

| Field | Meaning |
| --- | --- |
| `user_id`, `date` | key; unique index `{user_id: 1, date: -1}` |
| `eur_inr` | INR per 1 EUR, day close; absent when no rate is known |
| `fx_date` | trading day the rate belongs to (`YYYY-MM-DD`) |
| `fx_carried` | true when the rate is a fallback after a failed fetch, or missing |
| `stocks_invested_inr` | INR bucket invested + EUR bucket invested × `eur_inr` |
| `stocks_current_inr` | same for current |
| `updated_at` | last write |

Stock totals are absent when `eur_inr` is absent and the EUR bucket is
non-zero (no fabricated conversion). The legacy USD bucket is ignored, as
`/history` drops it.

`persistence.OverallStore` owns the collection. Only `SnapshotStore` writes
it, and `OverallService` and the backfill read it.

### 2.3 Write path: inside `SnapshotStore`

`SnapshotStore` gains an `overall *OverallStore` field, attached by
`Store.AttachOverall()` (the pattern of `AttachGold`). Production wiring
attaches it at its three entry points (`controllers.New`, `cmd/snapshot.go`,
`cliConnect`); a test asserts `controllers.New` does. `persistence.New`
alone leaves it nil, so the existing mock-driver tests' command sequences
stay exactly as they are. After each snapshot write, an attached store
refreshes the matching overall document from the row's **final** buckets:

| Method | After the snapshot write |
| --- | --- |
| `Upsert` | merged buckets are known. With `snap.Fx` (snapshot job): upsert the doc with that rate. Without (`RecomputeFrom`, History add / paste): the same refresh as below |
| `PatchRegion`, `PatchRegions` | read the row back, refresh with the stored rate: one pipeline upsert that multiplies by the overall doc's own `eur_inr`, so the overall doc is never read first. A date with no doc yet gets one with no rate and `fx_carried: true` (totals known when it holds no EUR; otherwise offered for re-fetch, §2.7) |
| `Delete`, `ForceDelete` | delete the overall doc |
| `DeleteByUser` | delete the user's overall docs |

`PortfolioSnapshot.Fx *FxRate` is `bson:"-"`: the snapshot job hands the
rate to the store without changing what a snapshot row stores. Because the
cron job, `RecomputeFrom` (ledger heal, trade import), manual History edits
and paste all write through these methods, none of them change.

The two writes are not atomic. A failed overall write returns its error to
the caller (the snapshot write is idempotent, so a retry converges). Any
drift is repaired by `migrate overall --rebuild` (§2.6).

### 2.4 Rate at snapshot time

`SnapshotService.Run` resolves the rate source once per run, only when its
`Overall` store is set (production wiring): for the current trading day the
live `EURINR=X` quote via `PriceFetcher.GetPrice`; for a past day the
historical close via `GetDailyCloses`, so a past row never gets today's
quote. "Current" is the job's own trading-day rule (`SnapshotTradingDay`,
moved from `cmd/snapshot.go` to `services/clock.go`): yesterday counts as
current only before the 08:00 IST cut-over. Per user:

| Day | Rate | `fx_date` | `fx_carried` |
| --- | --- | --- | --- |
| already stored and not flagged | kept (a re-run never overwrites it) | stored | false |
| current trading day (08:00 IST cut-over, `SnapshotTradingDay`), live fetch ok | fetched | row date | false |
| past weekday (`snapshot --date`) | that day's historical close (else the last before it) | close's day | false |
| weekend | prior doc's rate | prior doc's `fx_date` | prior doc's flag |
| weekday, fetch failed | prior doc's rate | prior doc's `fx_date` | true |
| no prior doc and no rate | absent | — | true |

### 2.5 Read path

`GET /history/overall?from&to` (`OverallService.Series`):

1. Read `portfolio_overall` for the user and range (ascending).
2. Gold, for a gold-enabled account: `GoldService.HistoryOverlay` (nearest
   earlier price, so a day without a price copies the previous day's, owner
   2026-11-18) plus the new `GoldService.HeldOn` (gold held on each day, the
   overlay's own existence test). If Postgres is not configured or either
   read fails, the response sets `gold_unavailable` and **every amount is
   absent**: a stock-only figure never passes as the overall total (owner,
   2026-11-18).
3. Per day: `invested_inr = stocks_invested_inr + gold invested`, likewise
   current; `invested_eur = invested_inr ÷ eur_inr` (null when no rate).
   Days without stock totals carry `missing_rate: true` and null totals.
   A day on which gold was held but had no price yet (bought before the
   first price entry) is `gold_unvalued: true` with absent amounts (owner,
   2026-11-18); entering the price heals it on the next read. A day before
   any gold was held has no gold and keeps its stock totals.

The response is daily points. The frontend reuses `flowAdjustedReturnPct`
and `pnlPct` (`features/history/historyShared.ts`), so the volatility
definition stays single-sourced, then thins 1Y / All to the last point of
each week for drawing. 10 years is about 3,650 points (about 250 KB JSON).

### 2.6 Backfill and repair (`migrate overall`)

`migrate overall [--dry-run] [--rebuild] [--user <id>]`, plus tracked step
`20261118_02` that runs the apply form:

1. Per user (cursor = last user id done), read the snapshot rows **and**
   the existing overall docs first. A day whose doc has a rate is "rated":
   apply skips it, rebuild keeps its rate.
2. Only if some day is not rated: one Yahoo call for `EURINR=X` daily closes
   over those days (`PriceService.GetDailyCloses`). Rate = close on that
   day, else the last close before it (holiday / weekend, `fx_carried`
   false); none before → absent, `fx_carried` true. A rebuild with every
   rate stored never calls Yahoo.
3. Write only days with no doc or a doc without a rate (`FillUnrated`:
   filter `eur_inr` absent, upsert; a duplicate key means "already rated"
   and is skipped). A doc the snapshot job wrote live is never overwritten.
   `--rebuild` instead recomputes stock totals from the row's buckets and
   **keeps** the stored rate.
4. `--dry-run` makes apply's exact selection and writes nothing. It logs
   per user: `rows`, `skipped_rated`, `to_write`, `without_rate`, and
   min / max `stocks_current_inr` over `to_write` only.

`portfolio_snapshots` is only read. Safety: `mongodump --collection
portfolio_snapshots` before the first prod run, dry run reviewed by the
owner, then apply; post-check counts snapshot rows before and after
(unchanged).

### 2.7 Missing-rate prompt (wave 4)

`GET /history/fx-missing` lists the caller's days with `fx_carried`.
`POST /history/fx-refetch {dates}` refetches those days via
`GetDailyCloses`, rewrites each doc's rate and stock totals (from the
snapshot row's buckets), clears the flag, and returns the dates still
missing. The History page shows the prompt for own portfolio only, not in
act-as; **Not now** hides it for the visit.

Wave 4a ([plan](../plans/PD-059-wave4-fx-refetch.md)) fixes the details:
both endpoints use one `FxDates {dates}` shape, newest first. Only
requested days that are still flagged are fetched; others are ignored. One
`GetDailyCloses` call covers the span and `rateOn` picks each day's rate;
the current trading day uses the live quote, as the snapshot job does. The
heal is a conditional update on `fx_carried: true` and the `updated_at`
read with the list, without upsert, so neither a good rate nor newer
totals from a History edit are overwritten; a day changed meanwhile stays
flagged for a retry. A failed fetch answers `200` with every day still
flagged. Owner (2026-11-19): UI_2.0 only; a partial result keeps
the dialog open with the remaining dates; Not now lasts until the app
reloads; the dialog lists 10 dates and "and N more".
